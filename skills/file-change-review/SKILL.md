# 文件改动审查

以当前项目证据回答：每处改动是否属于目标、是否构成最小完整实现、原功能是否保留，以及用户会受到什么影响。

## 范围与权限

- 本技能只读：不修改、格式化、清理业务工作区，不 stage、commit、push。用户已明确授权修复时，完成必要审查后进入对应实现流程；本技能本身不扩大授权。
- 本技能负责文件与 hunk 的必要性、完整性和影响审计；`code-review` 负责用户要求的 blocker-first 正确性与放行审查，`review-one-stop` 负责明确请求的交付编排。不为普通文件审查串联加载其他技能。
- 未要求合并门禁时只写“需要修正”或“未发现确认问题”，不主动给出可合、不可合或放行结论。缺证据写明缺口，不制造 finding。

## 按需读取

入口保留共同规则。仅在命中以下条件时读取相应细则，不整包加载：

## 审查步骤

### 1. 冻结当前基线和独立目标

1. 明确对象：工作区、指定文件、commit range、分支 diff 或 PR；记录 checkout、branch、HEAD、实际 diff，区分 staged、unstaged、untracked 和并发改动。列全业务、测试、配置、依赖/锁文件、文档与生成文件。
2. 范围依据优先用户目标/需求；已有 commit 读取 subject/body，待提交工作区使用用户提供的说明。没有独立依据标“目标证据不足”，不得用 diff 自证必要性。
3. 读取当前生效的项目指令、触达 owner 文档、配置、源码和验证脚本；历史记忆、旧分支与通用最佳实践只作线索。“最新”必须实际核验指定远端或提交，否则写“按当前本地基线”。

所有确定结论同时满足 `当前项目基线`、`最小充分约束`、`与风险匹配的验证`。约束须有来源、适用范围和违反后的具体失败；缺任一项就保留未验证边界或降为“证据不足”，不升级未来治理为本次门禁。

### 2. 建立功能和文件影响

- 对每个文件读取 diff、基线版本及必要上下文，沿入口、状态 owner、消费者、IO/副作用、异常和清理路径追踪，不能只看增删行。
- 以相同用户、前置条件、入口和操作建立功能点 F：分别记录 `改前预期`、`改前实际`、`改后预期`、`当前实现/实测`、差异结论。区分新增、修复、规则变化和内部支撑；旧行为不是正确预期，修改意图不是需求事实。无依据写“证据不足”。单文件、存在 finding 或纯内部改动也至少保留一行。
- 每个 diff 文件记录改前职责、功能影响、保留或替代路径及功能丢失结论，固定使用：`否`、`是（按需求移除）`、`是（移除意图待确认）`、`是（非预期丢失）`、`高疑似`、`证据不足`、`不适用（新增文件）`。按需求移除仍是移除，但不自动成为 finding；文件存在/删除本身不证明能力是否丢失。
- 每个功能点和文件说明受影响用户/条件、入口/平台/版本范围、直接用户结果、间接消费者与结果及有证据的不受影响边界。“内部改动”或“未改该文件”不能替代执行链证据，潜在影响与确认影响分开。
- 改动已有功能时建立 `场景 S -> 功能影响点 I -> 验证点`：每个 I 写清变化和必须保护的原行为，并有对应前置条件、操作/输入、判定 Oracle、验证层级、状态。仅新增独立方法可将已有功能影响写“不适用”，仍须验证消费者和新增能力。
- 增量功能分别标记 API、Native、埋点为 `触达`、`不涉及（有依据）` 或 `证据不足`；仅沿当前执行链判断，触达项按边界细则冻结允许变化、原行为和验证。
- 改动 Android/iOS 实现必须读取另一端 owner，显式判断业务契约和用户结果是否一致；缺另一端或关键分支证据只能写“证据不足”。语言/结构不同不等于逻辑不一致，不授权机械同步另一端。

### 3. 判断最小必要性和实现合理性

1. 写独立目标、非目标和直接实现、协议/平台接线、迁移、配置/生成物、必要验证组成的最小完整集合；最小不等于最少文件或行数。
2. 每个文件和可独立 hunk 映射到直接需求、必要支撑、问题修复、顺带整理或待确认，检查功能点、执行链位置、当前消费者及移除后的具体失败。
3. 保留其他改动、反事实移除本项，使用 `必要/有条件必要/冗余/过度改动/证据不足`。无独立贡献是冗余；有作用但超出当前目标是过度改动。必要性不等于合理性，同一文件可含不同分类 hunk。
4. 保持已有代码原位，只做目标必需的最小接线。触达已有功能须证明为何不能保持原行为，并映射影响与验证；新独立逻辑有清晰输入输出、单一 owner 和当前消费者时优先独立文件，不借抽取搬迁旧逻辑，不新增空壳/无消费者抽象。
5. 核对状态唯一 owner、输入输出/错误/取消/重试合同、异步与生命周期清理、抽象的稳定不变量、直接相关测试和反向消费者。出现两次不证明应抽象，用户不可见不证明支撑多余，绿色测试不证明每项必要。
6. 每项冗余或过度改动记录位置、当前目标、分类、移除影响、证据等级和最小收口建议，只提出建议。生成物/锁文件追溯源和生成原因；安全临时环境的删减 A/B 可作证据，不修改业务工作区或机械逐行删减。

### 4. 校准问题与验证

- 只报告当前 diff 引入、放大或暴露且条件可达的问题/隐患，确认问题须闭合入口到结果。写最小位置、条件、破坏的不变量、用户现象、范围和可恢复性；无因果关系的旧问题不归因当前改动。
- 每个可独立复现、修正或验证的问题用唯一 P?，在结论、风险、复现中复用；仅根因、修正方向和验证门禁相同才合并。P0–P3 影响优先级需有明确条件、实际影响和代码位置，本身不是合并门禁。
- 分别填证据等级 `运行实锤/测试实锤/代码实锤/高疑似/猜测/待确认` 和发生频率 `稳定复现/偶现/频率待确认`。静态链闭合仍写“运行待验证”；稳定复现须控制关键条件并重复触发，偶现须有真实样本。稳定测试不外推为真实用户运行。
- 每项问题/隐患给用户画像和绑定的复现路径；未实测只写“按代码推导，待实测确认”，类型为“候选复现路径/待验证”。猜测以“尚未确认用户问题”开头；仅数据影响写“前台无明显表现”及数据结果。
- 每个用户可感知功能点无论有无 finding 都给验证：前提、入口/动作、改前/改后预期、观察点、状态；必要时基线/当前版本在相同条件下做最小 A/B。
- 选择当前项目能证伪风险的最小验证，owner 专项门禁优先。局部风险不扩大全仓，跨 owner/公共契约/异步/持久化补对应合同或集成，高风险按项目要求补平台或运行证据。静态、测试、设备/UI、网络、后台证据不能互相冒充。
- 风险不增加设备、账号、后台或外部操作授权；缺授权或未执行则报告缺口。输入/实现/环境未变可复用已通过结果，测试只证明覆盖合同；建议清理后的最终证据须来自获授权清理后的代码。

## 报告与收口

生成报告时读取输出合同，不重复流程叙述。保留全部 diff 文件和功能点覆盖，机械生成且字段完全相同的文件可列全路径合并；文件多时只展开有问题、冗余、过度或证据不足项的详细证据。

首段按文件一级编号、字段二级编号逐行给结论：文件用途、改动位置、改动用途、为什么要改、不改动有什么影响、必要性、隐患；每条独立隐患另占一项，原生实现追加另一端语义结论，全部文件后给整体判断。强制矩阵、固定状态和影响/验证映射按输出合同保留，不能以 finding、测试绿色或追求简洁代替。
