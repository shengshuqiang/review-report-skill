# 最小完整改动的细判

在多文件、混合 hunk、重构、移动、抽象或支撑清理需要细判时读取；普通局部审查使用入口的反事实规则即可。

## 分类及反事实

| 结论 | 判断依据 |
| --- | --- |
| 必要 | 移除直接破坏当前需求、契约、构建、兼容性或必要验证 |
| 有条件必要 | 仅特定平台、数据、后端契约、发布方式或关联改动成立时需要，明确条件 |
| 冗余 | 无独立贡献；移除后行为、契约、构建、迁移和必要验证不变，或已由同轮其他变化完整覆盖 |
| 过度改动 | 有效但超当前目标：提前通用化、顺带重构、扩大主流程或无当前消费者的未来能力 |
| 证据不足 | 缺目标、消费者、依赖或失败语义，写最小补证据动作 |

不要用“非必要”混淆冗余与过度；不能区分就写证据不足。必要但实现不合理、实现合理但超范围都可能成立。

- 目标须来自用户/需求/issue/提交说明等独立依据，不能从 diff 反推后自证。
- 每个可独立 hunk 有一个可说明的理由，混入无关功能、治理或修复分别标过度或待确认。
- 固定保留其余改动、反事实移除本项，检查目标行为、既有契约、构建兼容、数据安全、双端一致性和必要验证。
- 同一文件可含必要与过度 hunk；整体必要不覆盖局部扩张，局部冗余不否定整文件。
- 错误处理/清理配对、类型闭合、迁移、平台接线和直接相关测试即使用户不可见也可能必要，先说明移除失败。
- 局部方案未被证伪却扩展主流程、多个核心模块、新状态机或通用框架，至少标“高疑似过度改动”及缺失的必要性证据；不凭文件数量或复杂程度定罪。

## 职责与位置

1. 保持已有文件、方法、语句位置。只有目标行为、语言/框架、依赖方向或测试接线确实要求才移动，否则重排、改名、格式化、目录迁移和搬运不是必要增量。
2. 只有新增具有当前消费者的独立方法，且不改既有入口、调用、条件、状态、副作用、返回契约，才算“仅新增独立方法”。其余触达都解释为何不能保持原行为、保持后如何失败，并给影响场景/影响点/对应验证。
3. 清晰输入输出与单一 owner 的独立新逻辑默认放职责明确的独立文件，原 owner 只保留必要导入、调用、注册或渲染；不借隔离移动旧逻辑。
4. 只用一次不充分证明无需隔离，出现两次不充分证明应抽象。空壳 wrapper、重复转发、无稳定边界通用层、未来扩展点和无消费者导出属于冗余或过度。
5. 判断职责和文件数量是两回事，小文件减少旧 owner 侵入且无额外抽象可更小、更安全；“更整洁/更健壮/以后需要”不是本次门禁依据。

## 反向依赖

- 以最终 diff 查新增文件、导出、配置、mock、依赖、bridge、feature flag、兼容分支、临时日志、生成支撑的真实消费者，同轮替代实现的旧支撑尤其容易遗留。
- 找不到消费者，或等价移除后行为不变且直接验证通过，判冗余。特殊支撑至少说明消费者、移除失败和对应验证。
- 可在安全临时环境做独立删减 A/B 与直接验证；不能试验时用消费者和失败语义判断，不修改业务工作区或机械逐行删减。
- 建议移出本次改动、回退局部 hunk 或另立任务即可；未要求方案不扩展重构设计。
